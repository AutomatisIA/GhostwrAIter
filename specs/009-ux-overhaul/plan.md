# Implementation Plan: UX Overhaul

**Branch**: `009-ux-overhaul` | **Date**: 2026-04-12 | **Spec**: [spec.md](spec.md)

## Summary

Refonte complète de l'expérience utilisateur de LinkedIn Poster : réduction de la navigation de 8 à 5 entrées, fusion Idées+Atelier en un écran "Créer" sans page vide, headers compacts, dashboard transformé en cockpit actionnable, bibliothèque avec planification intégrée, page paramètres complète avec thème dark/light et diagnostics, et abstraction multi-CLI pour supporter Codex, Claude Code et Gemini CLI.

## Technical Context

**Language/Version**: TypeScript 6.0.2  
**Primary Dependencies**: React 19.2.5, React Router DOM 7.14, Electron 41.2.0, electron-vite 5, Vite 7.3.2

**Project Type**: Desktop app (Electron)  
**Performance Goals**: Theme switch < 100ms perçu, aucune page vide, 2 clics max pour commencer une rédaction  
**Constraints**: Local-first (constitution I), zero SaaS, offline pour le non-génératif  
**Scale/Scope**: 5 écrans, ~40 FR, 1 utilisateur local

## Implementation Phases

### Phase A — CSS Theme Foundation (FR-024 to FR-028)

Migrer tous les ~60 color values hardcodés vers des CSS custom properties. Créer les deux palettes (light/dark). Ajouter le mécanisme de switch.

**Scope**: `styles.css` uniquement + persistence (app_settings table + IPC).

**Approach**:
1. Créer la table `app_settings` dans `init-database.ts`
2. Créer `settings.service.ts` avec get/set preference
3. Ajouter les IPC channels `settings:get-preference` et `settings:set-preference`
4. Extraire les couleurs en semantic tokens CSS (`--color-bg-*`, `--color-text-*`, `--color-border-*`, `--color-accent-*`)
5. Définir `:root[data-theme="light"]` et `:root[data-theme="dark"]`
6. Appliquer `data-theme` au démarrage depuis main process (via preload)
7. Créer `ThemeSelector` component (3 options: System, Light, Dark)

**Risk**: La migration CSS est large (~60 valeurs) mais mécanique. Le glassmorphism nécessite des ajustements d'opacité pour le dark theme.

### Phase B — Navigation Restructure (FR-001 to FR-003, FR-009 to FR-011)

Réduire de 8 à 5 routes. Headers compacts. Redirects.

**Scope**: `App.tsx` + removal of eyebrows/descriptions across all screens.

**Approach**:
1. Modifier le `sections` array dans `App.tsx` : 5 entrées
2. Ajouter des `<Navigate>` pour les anciennes routes
3. Réduire h1 à `1.4rem`, supprimer `max-width: 14ch`, supprimer eyebrows
4. Supprimer les paragraphes de description sur tous les écrans
5. Mettre à jour la sidebar (labels, ordre)

### Phase C — Create Screen (FR-004 to FR-008, FR-006a)

Fusionner Idées + Atelier en un écran unique avec remplacement progressif.

**Scope**: Nouveau `CreateScreen` + `IdeaSelector` component. Réutilise `useWorkshopFlow` et tous les workshop sub-components.

**Approach**:
1. Créer `CreateScreen` avec state machine : `selecting` | `workshop`
2. En mode `selecting` : afficher `IdeaSelector` (liste d'idées + 3 modes de création)
3. En mode `workshop` : afficher le layout existant (WorkshopGuide + panels)
4. Bouton "Changer d'idée" visible pendant le workshop
5. Supprimer `IdeasScreen` et `WorkshopScreen` (code migré)

### Phase D — Cockpit (FR-012 to FR-015)

Remplacer le Dashboard par un cockpit actionnable.

**Scope**: Nouveau `CockpitScreen`. Réutilise les IPC existants (strategy bundle, ideas list, library entries, calendar items, diagnostics).

**Approach**:
1. Pipeline progress bar : calculée depuis les compteurs existants
2. Next action recommandée : logique conditionnelle (if !strategy → "Créer votre stratégie", if !ideas → "Ajouter une idée", etc.)
3. Métriques cliquables avec couleurs de statut
4. Premier lancement : assistant 3 étapes (détecté via strategy empty + ideas empty + drafts empty)

### Phase E — Library with Planning (FR-016 to FR-018)

Ajouter un sélecteur de vue (Drafts/Planning) et la planification inline.

**Scope**: Modifier `LibraryScreen`. Absorber la logique de `CalendarScreen`.

**Approach**:
1. Tab switcher "Drafts" / "Planning" en haut de l'écran
2. Vue Planning : liste chronologique triée par date (porte le rendu de CalendarScreen)
3. Planification inline : bouton "Planifier" sur chaque draft → popover date picker + confirmation
4. Supprimer `CalendarScreen` (code migré)

### Phase F — Settings Overhaul (FR-019 to FR-023)

Page Paramètres structurée en sections avec diagnostics intégrés.

**Scope**: Refonte de `SettingsScreen`. Absorber `ExecutionScreen`.

**Approach**:
1. Layout en sections collapsibles : Apparence, Moteur, Diagnostics, Données
2. Section Apparence : `ThemeSelector` (de Phase A)
3. Section Moteur : `EnginePanel` (affiche les CLI détectés, sélection active)
4. Section Diagnostics : `DiagnosticsPanel` (porte le rendu de ExecutionScreen)
5. Section Données : export + purge (existant)
6. Supprimer `ExecutionScreen` (code migré)

### Phase G — Multi-CLI Engine (FR-029 to FR-038)

Abstraction du runner pour supporter Codex, Claude Code, Gemini CLI.

**Scope**: Nouveau `CliEngine` interface + 3 implémentations + engine registry + settings UI.

**Approach**:
1. Créer l'interface `CliEngine` (isInstalled, isAuthenticated, getStatus, executeSkill)
2. Extraire `CodexEngine` depuis `CodexCliRunner` (refactoring, pas réécriture)
3. Implémenter `ClaudeEngine` et `GeminiEngine`
4. Créer `EngineRegistry` : détection au démarrage, sélection, fallback
5. Modifier `SkillRunnerService` : déléguer à l'engine actif via registry
6. Modifier `ExecutionDiagnostics` : nouveau shape avec engines[]
7. Compléter `EnginePanel` : affichage 3 états par CLI, commandes copiables, guidance d'installation
8. IPC channels : `settings:detect-engines`, `settings:get-active-engine`, `settings:set-active-engine`

**Risk**: Les formats d'invocation Gemini CLI et Claude Code CLI sont basés sur la documentation actuelle et des hypothèses raisonnables. L'adaptateur doit gérer gracieusement les échecs de format.
